# wasmtime 48 and the draft WIT: the pre-build check for #27

Syrinx's plugins are WebAssembly components (owner decision of 2026-10-15),
run by wasmtime pinned on its 48.x long-term-support line (decision 1 of
2026-10-21) against one typed interface, the `syrinx:plugin` WIT package.
Before #28 builds the host crate, the owner wanted three things known rather
than assumed: what the wasmtime dependency brings into Syrinx's graph, that
the draft interface actually parses and loads on Windows, and that the two
sandbox tools the design leans on, the epoch deadline and the memory cap, do
what research note 10 says they do. Decision 2 of 2026-10-24 folded these
"Plugin runtime 0" checks into #27 and allowed them before Plan 1's exit on
one condition: throwaway builds outside the repository only, nothing under
`crates/`, nothing built in this repository. This report records what was
checked on 2026-10-24, how, what came out, and what #28 must do differently.
The dependency audit itself is `docs/dev/wasmtime-audit.md`.

It was revised the same day after the independent review of #158. The review
found that the pin fails Syrinx's D9 network gate, which the first version
missed; that is now the first item in "Owner decides", and a second throwaway
host, without `wasmtime-wasi`, was built and run to price the main
alternative. The review's other corrections are made where they belong, and
the test outcomes are recorded under "Test runs" so that they stand without
the scratch logs.

**Terms.** A *component* is a WASM binary in the component-model format,
exchanging typed values. A *world* lists what a component imports (what Syrinx
offers) and exports (what the plugin offers). `wasmtime::component::bindgen!`
generates the host side of a world from the `.wit` files; `wit_bindgen::generate!`
generates the guest side. A *store* holds the state of the instances created
in it; a *trap* is an unrecoverable stop (a deadline, an out-of-bounds access,
a Rust abort), and it marks the whole store as trapped.
`@since(version = x)` marks an addition that stays compatible from that version
on; `@unstable(feature = f)` marks an item hidden unless the feature is on.

## The WIT draft on Windows

**It parses and loads.** The 0.1.0 package as the template ships it parses
with and without features, `bindgen!` generates the host for it, and both
0.1.0 guests instantiate and answer every export that was called. With
`all_features` on, `host` has ten functions (the gated `widget-changed`
included); without, nine. No export of `widgets` appears in either reading,
which is the template's finding 3 holding on Windows.

**Interface names carry the version, and `Component::component_type()`
exposes them before instantiation.** The full guest reports the imports
`syrinx:plugin/types@0.1.0` and `syrinx:plugin/host@0.1.0` and the exports
`syrinx:plugin/lifecycle@0.1.0`, `commands@0.1.0`, `forms@0.1.0`,
`views@0.1.0`, `search-feed@0.1.0` and `events@0.1.0`; the 0.1.1 guest
reports the same names at `@0.1.1` plus `documents@0.1.1` and `watch@0.1.1`
among its imports. A host can therefore read a component's track from its
names, as note 10's scheme assumed (⚠️ now resolved).

**Which WASI 0.2 imports Rust's standard library brings**, for
`wasm32-wasip2` on `rustc 1.97.0`, read from each component's
`component_type().imports()`. Every guest imports at least these fourteen
interfaces, all at `0.2.9`, the fourteen the template found on Linux:
`wasi:io/poll`, `wasi:io/error`, `wasi:io/streams`,
`wasi:clocks/monotonic-clock`, and `wasi:cli/stdout`, `stderr`, `stdin`,
`environment`, `exit`, `terminal-input`, `terminal-output`, `terminal-stdin`,
`terminal-stdout` and `terminal-stderr`. Ordinary code adds two more, which
the first version of this report missed because its guests did not use that
code. **A guest that uses `HashMap` imports `wasi:random/insecure-seed`** for
the hash seed, and the real Notes 1 component does. And the full guest, once it
had its new commands, imports `wasi:clocks/wall-clock` (its `now` only; which
standard-library call pulls it was not traced). A guest that touches files
imports `wasi:filesystem/types` and `preopens`. No guest imported sockets or
HTTP. So a host for real plugins provides sixteen interfaces, not fourteen;
the template's test host already allows `wasi:random`.

**One world with default guest stubs works** (decision 5 of 2026-10-24). The
minimal guest, whose `forms`, `views`, `search-feed` and `events` are stubs
returning `not-found` or nothing, instantiates on the 0.1.0 host, runs its
one command, and answers `forms.form-for` and `search-feed.changes` with
`plugin-error.not-found`. A plugin therefore implements only what its
manifest declares, provided the template ships those defaults.

**Those stubs were written by hand, not generated.** wit-bindgen 0.63.0's only
built-in option, `stubs` (`wit-bindgen-rust-0.63.0/src/lib.rs`, line 188),
generates one `Stub` type in which every function is `unreachable!()`
(`interface.rs`, line 1493). Calling one traps and, as "The end-to-end run"
shows, poisons the store; it does not answer `not-found`. So the check proves
what is necessary, that a plugin whose unused exports answer `not-found`
loads, but not the "generated defaults" #27's box names. The open part goes
to #30: the template ships per-interface defaults as code, a macro for
example.

**Gated imports work both ways.** With `LinkOptions::home_widgets(false)`
the host does not link `widget-changed`; with it on, the host links one more
function than the guest imports, and the guest still loads, because an
instance may be given more than it asks for.

## Notes' paper shapes

Decision 6 of 2026-10-24 adds `documents`, `watch`, `drafts`, `editor` and
`open-external` to the package with `@since(0.1.x)` in the Notes slices,
after their paper shapes are reviewed here. Notes 1 drafted two of them, in
`Syrinx-Notes-Plugin/docs/host-contract-gaps.md` sections 1 to 3; the other
three are explicitly "not in Notes 1" (section 11), so there is nothing to
review yet and they go through the same probe when #37 drafts them.

Both drafted shapes were added to the 0.1.1 package verbatim first. Two
things stopped the parser, both names:

1. **`documents.list` is a WIT keyword.** `list: func() -> result<list<entry>, …>`
   fails with "expected `type`, `resource` or `func`, found keyword `list`",
   the same class of fault as the draft's `result` parameter that the template
   renamed to `outcome`. The throwaway calls it `list-entries`; the Notes
   repository chooses the final name (its `DocumentsApi::list` trait method
   mirrors it).
2. **`vault-state` names both a type and a function.** WIT keeps one namespace
   per interface, so `variant vault-state` and `vault-state: func()` are a
   "duplicate name". The throwaway renames the function `current-vault`.

With those two renames both interfaces parse, the gates read as
`Stable { since: 0.1.1 }`, and the 0.1.1 guest used them end to end: it
called `current-vault`, `list-entries`, `read` on the first entry and
`watch.poll(16)`, and logged `vault=Granted("Synthetic vault") entries=2
first_bytes=8 events=3 renames=1` against two synthetic documents and three
scripted events (a change, a rename and `overflow-rescan`). The variant
`event` with its `renamed(tuple<document-id, document-id>)` case, the `use
documents.{document-id}` across two since-gated interfaces, and the
`choose-vault` function all generate and link as drafted. The world's
`import documents;` and `import watch;` lines carry the gate as well as the
interfaces; that form is what was tested.

For the WIT package's documentation, the identifiers wit-parser 0.262.0
treats as keywords, which no interface, type, field or function may use
without `%` escaping: `as`, `async`, `bool`, `borrow`, `char`, `constructor`,
`enum`, `error-context`, `export`, `f32`, `f64`, `flags`, `from`, `func`,
`future`, `import`, `include`, `interface`, `list`, `map`, `option`, `own`,
`package`, `record`, `resource`, `result`, `s8`, `s16`, `s32`, `s64`, `static`,
`stream`, `string`, `tuple`, `type`, `u8`, `u16`, `u32`, `u64`, `use`,
`variant`, `with`, `world`.

Two observations for #36, not parse faults: `list-entries` returns the whole
vault in one call (the signature has no `max` or cursor), while #98 row 4
already asks for per-call budgets; a bounded shape would fit that better. And
bindgen turns the `document-id` and `command-id` aliases into `String`, so the
host's generated call signatures take `&String` where a `&str` would be
expected; harmless, but visible in #28's code.

## The version rules, observed

Note 10's table "What breaks a plugin" was inferred from the specifications;
four of its rows are now observed on Windows under wasmtime 48.0.7:

- **An import added with `@since(0.1.1)` is a compatible addition.** The
  0.1.0 full guest instantiates on the 0.1.1 host, whose linker defines
  `host@0.1.1`, `documents@0.1.1` and `watch@0.1.1`, and runs its commands and
  form. wasmtime's `Linker` matched the guest's `host@0.1.0` import to the
  host's `@0.1.1` definition, so semver-compatible naming works across a
  minor below 1.0, which the documentation left unstated (⚠️ resolved).
- **A plugin built for 0.1.1 needs a 0.1.1 host.** On the 0.1.0 host it is
  refused at instantiation with a usable message: "component imports instance
  `syrinx:plugin/documents@0.1.1`, but a matching implementation was not found
  in the linker: instance export `current-vault` has the wrong type: function
  implementation is missing".
- **An export added in a minor breaks every older plugin, `@since` or not.**
  With `watch-sink` exported `@since(version = 0.1.1)`, the 0.1.0 guest fails
  with "no exported instance named `syrinx:plugin/watch-sink@0.1.1`", exactly
  the template's finding 3 for `@unstable`, because `bindgen!` resolves every
  gate and `instantiate` requires every export it knows.
- **A function added to an existing export breaks every older plugin the
  same way.** With `cancel: func(view: view-instance, request-id: request-id)`
  added to `views` as
  `@since(version = 0.1.1)`, the 0.1.0 guest fails with "instance export
  `syrinx:plugin/views@0.1.1` does not have export `cancel`", because
  `bindgen!` looks up every function of every export.

The rule this gives, worded as the review proposed: **within a minor track
(0.1.x), only new imported interfaces, and new functions or types inside
imported interfaces, may be added, each `@since`. No export, no exported
function and no existing item changes. Anything else opens a new minor track
with its own `bindgen!` module** (note 10's scheme, item 4), or goes in a
separate world. Home widgets are such a case: the template's wording, that
widgets "should arrive as an `@since` addition on a later minor"
(`syrinx-plugin-template/docs/wit-changes.md`), holds only if that addition is
an import, so #31 should plan for a track, not a gate. Notes' five capabilities
are all imports, so decision 6 is unaffected.

## The end-to-end run

- **An expired deadline traps.** `test.spin` trapped after 504.8 ms and, in
  the rerun, 512.8 ms against a 500 ms budget, with `Trap::Interrupt` ("wasm
  trap: interrupt"), under a ticker advancing the epoch every 10 ms. A further
  call on the same store then failed with `Trap::CannotEnterComponent` ("wasm
  trap: cannot enter component instance"), which the test now asserts rather
  than prints. **A trap poisons the whole store, not just the instance that
  trapped.** Any trap sets one `trapped` flag per store
  (`wasmtime-48.0.7/src/runtime/func.rs`, line 1480; `component/store.rs`,
  line 42, "Whether an instance belonging to this store has trapped"), nothing
  resets it, and with the component model's concurrency off `may_enter`
  returns its negation (`concurrent_disabled.rs`, line 178). So every
  component instance in that store is refused, a store must hold one plugin
  instance and never be shared, and note 10's rule that a trapped store is
  discarded is not merely conservative, it is the only thing that works. The
  real host must therefore keep its re-instantiation path cheap (the
  compiled-code cache of #137 is what makes it so) and mark in-flight writes
  `uncertain` as planned.
- **The memory cap refuses growth.** With `StoreLimitsBuilder::memory_size`
  at 8 MiB, `test.grow` started at 17 pages (1.06 MiB, Rust's initial memory)
  and was refused after 111 more, at exactly 128 pages; `memory.grow`
  returned -1 to the guest, the guest reported it as a typed
  `plugin-error.unavailable`, and the instance stayed usable (`test.echo`
  ran afterwards). That is the shape when a guest checks the result itself.
  **`memory_size` caps each linear memory, not the store** (wasmtime's
  `runtime/limits.rs`, line 233: "applied to each linear memory
  individually"). The first run allowed four memories, so a store could have
  reached 32 MiB. Every component here, the five guests and Notes 1, has
  exactly one linear memory: all of them instantiate with `memories(1)`, which
  the reruns use, and with that setting `memory_size` is the store's
  budget.
- **A real allocation past the cap traps.** `test.alloc`, which pushes 1 MiB
  `Vec`s, ended in `Trap::UnreachableCodeReached` ("wasm `unreachable`
  instruction executed"): Rust's allocator calls `handle_alloc_error`, which
  aborts under `panic = "abort"`. This is how an ordinary plugin meets the
  cap, so #28's "`test.grow` refused by the memory cap" test should expect a
  trap for ordinary code and a typed error only for a guest that probes
  `memory.grow` itself. After this trap too the next call is refused with
  `Trap::CannotEnterComponent`; the first version said "as above" without
  trying it, and the test now asserts it.

Nothing here is a measurement: the thirteen tests, compiling five components
with Cranelift included, ran in 2.4 s on this machine, but #28's Windows
measurements (decision 3) are the figures to design from.

## Owner decides: WASI and the network gate

The review found, and main's own gate confirms, that the pin as #27 lists it
fails `cargo xtask check-deps` on D9: `io-extras 0.19.0`, which
`wasmtime-wasi` pulls through `cap-primitives`, asks the shared
`windows-sys 0.60.2` build for WinSock, which none of the eight approved
entries covers (`wasmtime-audit.md`, "Windows networking (D9, DW-68)").
D9 and DW-68 make the network the owner's call, so this section sets out the
ways forward with what each was shown to cost. Nothing in the repository's
xtask policy or Cargo files was changed; the gate variants ran on a scratch
copy of main.

### (a) Choose features so the networking crates drop out

Not possible within #27's list. `wasmtime-wasi 48.0.7`'s features are `p0`,
`p1`, `p2` and `p3`; its one optional dependency is `wiggle` (for `p1`);
`tokio` (with `net`) and `cap-primitives` (which brings `io-extras` and its
WinSock request) are unconditional. `p2` is the only one a component host
can use, since `p3` is WASI 0.3, which decision 1 of 2026-10-21 keeps off.
`wasmtime-wasi-io`, which holds only the I/O interfaces, offers
`add_to_linker_async` alone, and async execution is what note 10 rules out
for 0.1.0. `wasmtime` alone, with exactly #27's six features, resolves no
networking feature, so the smallest departure that passes is to drop
`wasmtime-wasi`, which is (b).

### (b) Drop `wasmtime-wasi`; Syrinx's host provides the WASI imports itself

Built and run in the throwaway as the shim host.

- **What it declares:** `wasmtime =48.0.7` with #27's six features and
  nothing else. Its own lockfile has 125 third-party packages and none of
  `tokio`, `mio`, `socket2`, `io-extras`, `cap-primitives` or
  `wasmtime-wasi`; its only `windows-sys` is 0.61.2. In Syrinx's workspace it
  adds 47 name-and-version pairs to the lockfile instead of 58, and the host's
  Windows build compiles 103 third-party crates instead of 170; the audit's
  "Windows networking" section lists what leaves. Main's gate passes, with the
  host inside `needs_shell_isolation` or not.
- **What it must provide:** the sixteen interfaces listed in "The WIT draft
  on Windows": `wasi:io/error`, `poll` and `streams`;
  `wasi:clocks/monotonic-clock` and `wall-clock`; `wasi:random/insecure-seed`;
  and the ten `wasi:cli` interfaces. `bindgen!` generates their host traits
  from the WASI 0.2.12 WIT that `wasmtime-wasi 48.0.7` ships
  (`src/p2/wit/deps`), copied: `io.wit`, `clocks.wit` and `random.wit`
  verbatim, and `cli.wit` without its two worlds, which name the filesystem,
  sockets and random interfaces. Guests import `@0.2.9`; wasmtime's `Linker`
  serves them from the `@0.2.12` definitions by the same semver matching that
  serves `host@0.1.0` from `@0.1.1`.
- **What it costs:** 43 functions in about 210 lines of code (274 with
  comments and blank lines), plus about 90 lines of state and helpers: the
  two bounded output buffers, the clock origin, the timer table and the
  reason a call was stopped. Twenty-eight of the functions return a constant,
  an empty value or `closed`: every `drop` but the timer's, `stdin`'s four
  reads, `check-write`, both flushes, both `subscribe`s, both splices, the two
  clock resolutions, the three `environment` functions and the six stream and
  terminal getters. The other fifteen are short, the longest (`poll`) ten
  lines: the four output writes, `ready`, `block`, `poll` and dropping a timer,
  the two `subscribe` functions of the monotonic clock, the two `now`s, the
  seed, and the two forms of `exit`. The whole throwaway library is 510 lines
  including the plugin world's own host functions. Beside that code it
  commits 692 lines of WASI WIT copied from the crate, which need their own
  ruling (below).
- **How it behaves**, each observed in a test:
  - Standard output and standard error go to two buffers in the store,
    capped at 64 KiB each; the rest is dropped and counted. After 4,001
    prints, 65,536 bytes were kept and 68,978 dropped. #28 would hand them to
    the plugin's log; `wasmtime-wasi` with an empty context discards them.
  - A panic writes its message to standard error ("synthetic panic", with the
    guest's file and line) before the `unreachable` trap, so the host can show
    why a plugin stopped; the next call is refused with
    `Trap::CannotEnterComponent`.
  - Standard input is empty and closed.
  - `exit` stops the call with a trap that carries a named reason ("the
    plugin called exit with Err(())"). `std::process::exit(3)` arrives as
    failure without its code, because the guest imports only WASI 0.2's
    `exit(result)`, not the unstable `exit-with-code`.
  - Sleeping is refused: blocking on a timer that has not expired
    (`std::thread::sleep(50 ms)`) stops the call with "the plugin tried to
    sleep, which plugins may not do". A synchronous host would otherwise block
    the plugin's thread; #28 may instead let a sleep run within the call's
    deadline. Either is a few lines.
  - The monotonic clock is the host's `Instant`, counted from the store's
    creation, with a 100 ns resolution (Windows' performance counter); a
    guest's 5 ms busy loop timed with `Instant` finished after 7,268 spins.
    The wall clock is `SystemTime`. The seed comes from the host's own
    `RandomState`, so it adds no crate.
  - The environment and the arguments are empty and `initial-cwd` is none;
    the guest never asks for the working folder anyway, because wasi-libc
    answers `/` itself. There is no terminal.
- **What it refuses:** anything else, at instantiation and by name. The
  filesystem guest gets "component imports instance
  `wasi:filesystem/types@0.2.9`, but a matching implementation was not found
  in the linker: instance export `descriptor` has the wrong type: resource
  implementation is missing". That is the refusal the review's S5 asks for,
  by construction rather than by care. The verification of #158 also built a
  sockets guest (`std::net::TcpStream::connect` to a documentation address).
  It imports seven `wasi:sockets` interfaces besides the filesystem ones,
  and the shim refused it before it ran.
- **The real plugin:** the Notes 1 component instantiates and activates on
  the shim host unchanged. It imports the fourteen, `insecure-seed`, and six
  of Syrinx's host functions.
- **What Syrinx takes on:** it owns this code and its tests instead of
  `wasmtime-wasi`'s; when the template's toolchain moves, a guest's imports
  must be listed again (a new import fails instantiation with its name, so a
  contract test catches it before a user does); and it forgoes
  `wasmtime-wasi`'s future fixes for these interfaces. Of `wasmtime-wasi`'s
  nine advisories so far, five concern the filesystem and three the WASI 0.1
  and 0.0 layers, none of which (b) compiles. The ninth, RUSTSEC-2026-0322,
  "Excessive allocated memory on the host when guests don't have stdio", is
  exactly a shim's situation: its output buffers are capped and
  `write-zeroes` is bounded, and #28's tests should keep any guest from making
  the host allocate on its say-so.
- **A second ruling: the WIT files it copies.** `bindgen!` needs the
  interface definitions as WIT text, so (b) commits four files copied from
  `wasmtime-wasi 48.0.7`'s `src/p2/wit/deps/`: `io.wit` (299 lines),
  `clocks.wit` (162) and `random.wit` (92) whole, and lines 1 to 139 of
  `cli.wit`'s 233, cutting the two worlds after them; 692 lines in all. Their
  SHA-256s are `96e206d0…f433`, `6ed8aa65…47cc` and `48578c40…e08f`, and
  `b3434fc7…9ca3` for the cut `cli.wit` (the original is `fb6ac5d2…3873`).
  Their licence, from three places:
  - **In the crate**, they fall under its `license = "Apache-2.0 WITH
    LLVM-exception"` and its `LICENSE`, the Apache License 2.0 with the "LLVM
    Exceptions" appended at line 205. The files carry no header or SPDX line
    of their own.
  - **As published by WASI.** wasmtime's `ci/vendor-wit.sh` at `v48.0.7`
    fetched them with `wkg get --format wit "wasi:cli@0.2.12"` and its three
    siblings, from the packages WASI publishes. WASI's own publishing workflow
    (`.github/workflows/publish-proposal.yml` at tag `v0.2.12`) labels every
    package `Apache-2.0 WITH LLVM-exception`. The
    `org.opencontainers.image.licenses` annotation on
    `ghcr.io/webassembly/wasi/cli`, `io`, `clocks` and `random` at `0.2.12`
    reads exactly that, which is the one SPDX expression that covers them.
  - **In the source repository**, `WebAssembly/WASI` at `v0.2.12` (commit
    `281ba75f`), `LICENSE.md` and each proposal's own `LICENSE.md` say the
    specification is published "under the W3C Community Contributor License
    Agreement", and GitHub reports the licence as `NOASSERTION`. That
    agreement is one contributors sign, not a licence for distributing the
    files. Its section 2.1 grants everyone a copyright licence to reproduce,
    adapt, distribute and sublicense the contributions, and section 2.2 asks
    that derivative works name the specification and its version. It has no
    SPDX identifier.

  AGENTS.md admits outside code "only under permissive licences (MIT,
  Apache-2.0, BSD) or as whole MPL-2.0 files", and it lists "code under a
  licence not listed above" among the things to ask first. Decision 2's
  exception names `Apache-2.0 WITH LLVM-exception` for the wasmtime family's
  crates as dependencies at their pinned versions. In `docs/decisions.md`'s
  words, "This does not approve another crate under that licence, a wasmtime
  line other than 48.0.x, or a general licence-policy expansion", and it says
  nothing of files copied into Syrinx's own tree. **So (b) needs a second
  ruling:** that these four files may be committed under
  `Apache-2.0 WITH LLVM-exception`, the licence both the crate and WASI's
  packages declare. They would sit in one folder with the crate's `LICENSE`,
  a change notice on `cli.wit` (Apache-2.0, section 4(b)), and a provenance
  note giving the source crate and version, the path, each file's SHA-256,
  the cut worlds and the WASI version; that note also meets the agreement's
  attribution. The files are not code to maintain, but Syrinx owns them and
  copies them again when it moves to a newer WASI 0.2 patch release.

  Three ways to avoid copying, with their cost:
  - **Register the sixteen interfaces by hand** with
    `Linker::instance("wasi:cli/stdout@0.2.9")`, `func_wrap` and `resource`,
    declaring the records and variants through wasmtime's `ComponentType`
    derives. No WIT text is copied. But the host types are written by hand,
    and a signature that drifts from the real one shows up only when a guest
    fails to instantiate, not when Syrinx compiles.
  - **Read the WIT from `wasmtime-wasi` at build time only**, as a
    `[build-dependencies]` entry. **The gate refuses it.** Main's
    `check-deps`, run on a scratch copy of `aa355b9` with exactly that
    declaration and `wasmtime` as the only run-time dependency, prints the
    same `windows-sys 0.60.2 … requested by io-extras 0.19.0` line. The gate
    reads every resolved package and its unified features, whatever the
    dependency kind.
  - **Copy them at build time from Cargo's registry cache.** This is
    fragile: the cache holds `wasmtime-wasi` only while something depends on
    it, and that dependency is what (b) removes.

  The recommendation is to ask for the ruling, and to fall back on
  registering by hand if the owner declines.

### (c) Keep `wasmtime-wasi` and grant exceptions to the network check

What the owner would approve:

1. A ninth entry in `THIRD_PARTY_NETWORK_FEATURES`: binding
   `windows-sys 0.60.2`, feature `Win32_Networking_WinSock`, requester
   `io-extras 0.19.0`.
2. If #28 puts the host under `needs_shell_isolation`, a change to xtask's
   policy, because the headless network-reach rule has no list of approved
   paths: either split the predicate, so the host is checked for shell crates
   but not for network reach, or add an approved path
   `syrinx-plugin-host -> wasmtime-wasi -> tokio`. Both are new gate code.

**Would it let Syrinx make a network call on its own? Not by itself.** The
entries change what the gate accepts, not what runs. With an empty `WasiCtx`
every address is refused and TCP, UDP and name lookup are off, so no plugin
can open a socket, and nothing in Syrinx calls these crates directly. But
tokio's networking, `mio`, `socket2` and `wasmtime-wasi`'s sockets
implementation would be compiled into `syrinx.exe`, `add_to_linker_sync`
would link the socket interfaces, and from then on a later change that called
`inherit_network()` or set a permissive `socket_addr_check` would pass the
gate unnoticed. Keeping plugins offline would rest on review of #28 and of
every later change, which is what DW-68 made the gate to avoid. (c) also keeps
the tokio advisory in play (move to 1.53.3) and still needs the host to link
interfaces one by one so that filesystem and socket imports are refused.

### (d) Other ways, not recommended

- **Guests for `wasm32-unknown-unknown`, made into components with
  `wit-component`.** They would import no WASI at all, so the host would need
  neither `wasmtime-wasi` nor a shim. Not tried: the target is not installed
  here and nothing was installed. It would change the build target of the
  template and of Notes, and the standard library there has no output and no
  clock (`println!` goes nowhere, `Instant::now` panics). A bigger change than
  (b) for less.
- **Patch `wasmtime-wasi`** to make `tokio` and `cap-primitives` optional: a
  new vendor patch the owner would have to approve and Syrinx would carry for
  the LTS line's two years, larger than (b)'s code.
- **Link `wasmtime-wasi` interface by interface** (io, clocks, cli and random
  only): it fixes what a plugin can reach but not the gate, since the crates
  are still compiled. It is part of (c), not an alternative to it.

### Recommendation: (b)

It is the only way the gate passes as the owner wrote it, so D9 stays enforced
by the machine rather than by review. Nothing that can open a socket or a file
is compiled into `syrinx.exe`, so `wasmtime-wasi`'s filesystem advisories and
RUSTSEC-2026-0386 stop applying to Syrinx's build, and the host compiles 67
fewer crates. Filesystem and socket imports are refused at instantiation by
construction. The price is about 300 lines of mostly constant host code that
#28's contract tests exercise anyway, plus 692 lines of copied WIT, and the
real Notes 1 component already runs on it. It changes #27's list in one
place: the pin becomes `wasmtime =48.0.7` alone. Beyond choosing (b), it
needs two owner rulings. The first is the licence of the four copied WIT
files (above); asking for it is better than registering the interfaces by
hand. The second touches the wording of decision 1 of
2026-10-21, which keeps "the component model and WASI 0.2" (unchanged under
(b): the shim implements WASI 0.2, and plugins still target `wasm32-wasip2`)
but explains `async` as "compiled in because `wasmtime-wasi` requires it".
Under (b) `async` is off and that sentence no longer holds, so choosing (b) is
the owner amending that sentence, which this report does not do itself.

## What #28 must do differently, or write down

1. **Settle the WASI question first** ("Owner decides"). Under (b), the pin
   is `wasmtime =48.0.7` alone. Port the shim into `syrinx-plugin-host` with
   its tests, link exactly the sixteen interfaces, and list a guest's imports
   again whenever the template's toolchain moves. Once the owner has ruled on
   the copied WIT, keep the four files in one folder with the crate's
   `LICENSE`, a change notice on `cli.wit`, and a provenance note in the shape
   of the `vendor/*.provenance.md` files: the source crate and version, the
   path, each file's SHA-256 and the cut worlds. If the owner declines,
   register the interfaces by hand instead. Under (c), make the gate
   changes the owner approves, link io, clocks, cli and random one by one
   instead of calling `add_to_linker_sync`, and check
   `component_type().imports()` before instantiating so a refusal names the
   interface.
2. **If `wasmtime-wasi` stays, move `tokio` to 1.53.3 in the same change**
   (`cargo update -p tokio --precise 1.53.3`). `wasmtime-wasi` makes Syrinx
   compile tokio for the first time, and the version Syrinx's lockfile holds,
   1.53.2, is in RUSTSEC-2026-0386's range. The affected functions are
   Unix-only, so Windows never compiles them, but the first build that
   compiles tokio should compile a clean one. 1.53.3 is the smallest patched
   version and stays off the 1.54 line, whose 1.54.0 was yanked. Under (b),
   tokio is not compiled for Windows and stays as it is.
3. **Port the template's licence check to Syrinx's gate.** Syrinx-app's
   `crates/xtask` has no licence check today: it checks crate boundaries,
   Windows features and network reach, and nothing reads a `license` field or
   pins a version, so the exact-version approvals are enforced only by
   review. Port `syrinx-plugin-template`'s `cargo xtask licences`
   (`xtask/src/licences.rs` with its `licences.toml`): a licence list over
   `Cargo.lock` with the LLVM-exception family by exact name and version (32
   crates with `wasmtime-wasi`, 29 without), `unicode-ident 1.0.26`,
   `foldhash 0.2.0`, the eighteen ICU crates and `encoding_rs 0.8.42`. It is
   new gate code with its own tests, so it belongs on #28's work list rather
   than being implied. It reads Cargo's metadata, not licence files, so the
   audit stays the evidence behind each entry.
4. **Add the pin without `cargo update`.** The seeded resolution keeps every
   existing version; a fresh one moves `unicode-ident` to 1.0.27 and the
   Unicode-3.0 ICU crates to 2.4.0, both outside their exact approvals, and
   until item 3 lands nothing would stop it. Expect, in the Windows build, 47
   new crates at 48 name-and-version pairs plus two new versions
   (`gimli 0.33.0`, `object 0.39.1`) with `wasmtime-wasi`, or 37 new crates
   plus the same two versions without it.
5. **Write the addition rule into the WIT package**, as worded in "The
   version rules, observed", and carry it to #31 (widgets). #28's own
   `views.cancel` (the template's finding 4) is exactly the case it forbids:
   as a function of an exported interface it cannot be added within 0.1.x,
   so it goes into 0.1.0 before the freeze or into a later track.
6. **One store per plugin instance, never shared, and design for a poisoned
   store.** A trap marks the whole store as trapped, and both the deadline and
   the memory cap end in a trap for ordinary code. The host discards the
   store, marks writes `uncertain`, and re-instantiates on next use. The
   contract tests (#28, #135) assert `Trap::CannotEnterComponent` on the next
   call after the deadline trap and after the allocation trap, as the
   throwaway now does.
7. **Set `memories(1)` beside `memory_size`**, so that the per-memory cap is
   the store's budget, and make the memory-cap contract test two tests: a
   `memory.grow` probe (typed error, instance survives) and an allocation
   (trap, store discarded).
8. **Parse the WIT in the gate with `wit-parser 0.254.2`**, the version
   wasmtime 48 already pulls, declared `default-features = false, features =
   ["std"]`. wasmtime's macro already resolves it with its defaults
   (`decoding`, `serde`, `serde_json` and `std`), so no crate is added either
   way, but the narrow declaration keeps xtask's own build small and keeps
   `wat` off, which would add a crate. 0.262.0 was used here only because it
   was already cached; the two versions' keyword tables are identical, so the
   list above holds for both. Ship that list with the package so Notes and
   Forge authors do not rediscover `list` and `result`.
9. **Rename before freezing:** `documents.list` and the `vault-state`
   function cannot stay as drafted. The review recommends `list-entries` and
   `current-vault`, the names the throwaway used, and settling the bounded
   shape (a `max` and a cursor) in #36 at the same time; the host half uses
   whatever the Notes repository chooses.
10. **Carry the stub defaults to #30:** the template ships per-interface
    defaults as code, a macro for example, because wit-bindgen's generated
    stubs trap instead of answering `not-found`.
11. **Harden the shim when porting it** (the verification of #158 found
    these in the throwaway):
    - Make `write` refuse contents longer than the last `check-write` permit,
      as WASI 0.2 requires and `wasmtime-wasi` enforces.
    - Compare `component_type().imports()` with the sixteen interfaces before
      instantiating, so a refusal lists every unsupported interface. A
      sockets guest was refused only for `wasi:filesystem/types`, its first
      missing import.
    - Cap the live timers in a store, beside the output buffers: each
      `subscribe-*` call adds an entry that stays until the guest drops it.
    - Count the bytes `write-zeroes` cuts off past the permit in
      `dropped_output_bytes`, without the throwaway's catch-all
      `unwrap_or(0)`.
